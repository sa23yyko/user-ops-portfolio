## 4. 独立用户运营项目定位

### 项目名称（工作名）
**《大学生英语学习产品用户增长与精细化运营模拟项目》**

可替换为更作品集化标题：
**《一个用户为什么留下来？——语言学习产品用户增长与精细化运营模拟项目》**

### 项目性质
个人独立模拟项目 / 用户运营实战项目

### 业务背景（模拟）
语言学习 App 面向有明确学习或考试需求的青年用户，包括：
- 四六级
- 考研英语
- 雅思/托福
- 职业证书/BEC
- 商务英语
- 日常能力提升

### 核心业务问题
> 用户下载并注册产品后，未能形成持续使用习惯。

拆成两个环节：
1. 激活不足：注册后未完成首次核心学习
2. 早期留存不足：完成首次学习后逐渐停止使用

研究主问题：
> 用户为什么来？为什么没有开始？为什么开始后又停止？

## 5. 项目第一版问题假设

### 假设 1：启动成本较高
用户有需求，但首次进入产品后不知道学什么、怎么开始。

### 假设 2：缺乏可执行学习规划
用户有学习意愿，但学习计划无法融入真实生活节奏，容易中断。

### 假设 3：早期正反馈不足
尤其词汇学习中，用户第一次学习后容易产生“记不住、看不到进步”的感受，成就感弱，降低继续使用意愿。

以上均为待验证假设，不是真实结论。

## 6. 核心指标体系

### 核心指标
**D7 留存率**

定义：
首次使用/注册后的用户中，在第 7 天再次发生有效使用行为的比例。

项目理由：
用于观察用户是否形成初步稳定使用习惯。

### 辅助指标
- 激活率
- D1 留存率
- D3 留存率（后续可补）
- 学习任务完成率
- 人均学习次数
- 流失率
- 召回率
- 活动参与率（后续）
- 付费转化率（后续，若设计商业化模块）

基础生命周期链路：
**注册 → 激活 → D1 → D7 → 稳定学习 → 沉默/流失 → 召回**

## 7. 第一轮模拟定性用户研究

### 访谈目的
研究英语学习 App 用户从下载、首次使用、二次使用到留存/流失/召回的过程。

### 访谈核心问题
1. 上一次使用英语学习 App 是什么时候？用什么 App？做了什么？
2. 为什么下载？当时有什么具体学习需求？为什么选择这个 App？
3. 第一次使用后，第二次什么时候打开？为什么又打开？
4. 后来使用频率发生了什么变化？第一次明显减少/停止使用时发生了什么？
5. 如果连续一周未使用，什么情况最可能让你重新打开？

访谈原则：
- 优先问真实行为与具体场景
- 避免“你喜欢吗”“你觉得好吗”等泛态度问题
- 继续追问“当时具体发生了什么？”
- 不提前暗示提醒、奖励、活动等答案

## 8. 8 位模拟用户样本

> 以下均为模拟用户，仅用于方法学习与独立作品集。

### U01 四六级冲刺型
- 21 岁，本科三年级，CET-6
- 痛点：不知道今天背多少，启动成本高
- 洞察：需求明确，但首日任务不清晰
- 召回/运营触发：低门槛小任务 + 目标进度
- 标签：启动困难型 + 明确考试目标型

### U02 考研长期型
- 23 岁，考研英语
- 痛点：计划过重，连续失败后挫败
- 洞察：不是无规划，而是规划过载
- 触发：动态调整学习计划
- 标签：长期规划型 + 任务负荷敏感型

### U03 雅思留学型
- 22 岁，目标雅思 7
- 痛点：内容太多，选择成本高
- 洞察：个性化推荐不足
- 触发：目标分数 + 薄弱项推荐
- 标签：高价值目标型 + 个性化需求型

### U04 托福留学型
- 24 岁，托福
- 痛点：练习后看不到结果变化
- 洞察：效果反馈不足
- 触发：薄弱项识别 + 进步可视化
- 标签：效果验证型 + 数据反馈敏感型

### U05 职业证书型
- 25 岁，BEC，实习/初入职场
- 痛点：只有碎片时间，产品任务过长
- 洞察：任务颗粒度与时间结构不匹配
- 触发：10 分钟任务
- 标签：碎片时间型 + 场景适配型

### U06 兴趣提升型
- 19 岁，无明确考试目标
- 痛点：学习紧迫性弱，不知道为什么今天要学
- 洞察：弱目标、弱驱动
- 触发：电影/音乐/热点等兴趣内容
- 标签：弱目标型 + 内容兴趣驱动型

### U07 职场提升型
- 27 岁，商务英语
- 痛点：学习优先级低，经常被工作打断
- 洞察：需要与真实工作场景建立强关联
- 触发：商务邮件等场景化内容
- 标签：低优先级型 + 场景价值驱动型

### U08 习惯打卡型
- 20 岁，综合提升
- 痛点：一次断签后产生放弃效应
- 洞察：连续激励机制可能反向导致流失
- 触发：补签/容错机制 + 成就反馈
- 标签：习惯养成型 + 激励敏感型

## 9. 质性编码方法

编码链路：
**用户原话 → 一级编码 → 二级洞察 → 生命周期环节 → 运营触发**

典型示例：
- “不知道今天背多少” → 启动困难 → 任务不明确 → 激活 → 低门槛新手任务
- “任务太多完成不了” → 计划压力 → 任务过载 → 留存 → 动态任务调整
- “内容太多不知道选哪个” → 选择困难 → 个性化不足 → 留存 → 个性化推荐
- “练了很久没看到变化” → 反馈不足 → 成长不可见 → 留存 → 学习报告
- “只有十分钟” → 时间碎片化 → 任务颗粒度不匹配 → 留存 → 10 分钟任务
- “没有考试所以不着急” → 目标弱 → 内在驱动力不足 → 活跃 → 兴趣/场景内容
- “工作太忙” → 时间冲突 → 学习优先级低 → 留存 → 场景化触达
- “不想断掉连续记录” → 激励机制 → 连续打卡驱动/反作用 → 留存 → 容错机制

## 10. 用户痛点聚类

综合 8 位模拟访谈，形成 6 类痛点：
1. 不知道如何开始
2. 学习计划与真实生活脱节
3. 内容太多、选择成本高
4. 学习进步不可感知
5. 用户目标/紧迫性不足
6. 打卡激励中断后产生负反馈

核心方法论结论：
> “留存低”不是一个单一原因，而是不同类型用户在不同生命周期阶段出现不同问题。

## 17. 漏斗 SQL 关键逻辑

### 注册人数
```sql
SELECT COUNT(DISTINCT user_id) AS 注册用户数
FROM user_events
WHERE event_type = 'register';
```

### 激活（注册当天 start_learning）
```sql
WITH registrations AS (
    SELECT user_id, event_date AS reg_date
    FROM user_events
    WHERE event_type = 'register'
)
SELECT COUNT(DISTINCT e.user_id) AS 激活用户数
FROM user_events e
JOIN registrations r
ON e.user_id = r.user_id
WHERE e.event_type = 'start_learning'
  AND e.event_date = r.reg_date;
```

### D1
```sql
WITH registrations AS (
    SELECT user_id, event_date AS reg_date
    FROM user_events
    WHERE event_type = 'register'
)
SELECT COUNT(DISTINCT e.user_id) AS D1留存用户数
FROM user_events e
JOIN registrations r
ON e.user_id = r.user_id
WHERE e.event_type = 'open_app'
  AND e.event_date = date(r.reg_date, '+1 day');
```

### D7
```sql
WITH registrations AS (
    SELECT user_id, event_date AS reg_date
    FROM user_events
    WHERE event_type = 'register'
)
SELECT COUNT(DISTINCT e.user_id) AS D7留存用户数
FROM user_events e
JOIN registrations r
ON e.user_id = r.user_id
WHERE e.event_type = 'open_app'
  AND e.event_date = date(r.reg_date, '+7 day');
```

> 找出“哪一类用户在哪一个环节更容易流失”。

### B. 行为路径分析
关键问题：
> 完成首次学习任务的人，D7 留存是否更高？

后续可比较：
- 首日完成任务 vs 未完成任务
- D1 回来但未完成任务 vs D1 完成任务
- 学习频次高 vs 低
- 不同 user_type
- 有/无召回行为

### C. 精细化运营策略
把“用户类型 × 生命周期”连接起来，设计：
- 新手任务
- 低门槛首日体验
- 21 天学习挑战
- 连续打卡/补签
- 个性化提醒
- 10 分钟碎片任务
- 学习进度/成长反馈
- 沉默召回
- 分群 Push/社群触达

### D. A/B 测试
后续模拟：
- A 版 vs B 版提醒话术
- 新手任务强度
- 激励机制
- 个性化推荐
- 召回策略

要求：
不能虚构“真实提升”，只能写：
> 在模拟实验框架中定义指标与评估方法。
若生成模拟实验数据，必须明确标“模拟”。

## 22. 不可虚构/不可误导清单

Codex 生成任何内容时必须遵守：

### 可以说
- “个人独立模拟项目”
- “模拟访谈”
- “模拟用户行为数据”
- “基于 1000 名模拟用户/7306 条模拟行为日志”
- “使用 SQLite + SQL 完成漏斗分析”
- “设计运营策略”
- “建立 A/B 测试框架”

### 不可以说
- “在扇贝实习”
- “使用扇贝内部数据”
- “真实访谈 8 位扇贝用户”
- “将 D7 从 23.7% 提升到 XX%”（除非明确写模拟实验）
- “推动真实营收增长 XX%”
- “上线某真实公司产品功能”
- “真实 A/B 实验提升 XX%”
